- 2026-09-10：旧检查日志明确出现 `inspection time limit reached after 10026 ms; read 18939904 bytes`，整文件检查会拖延异常收尾。按用户要求已删除该扫描路径，改用实时解码和实际输出结束事件；日常格式探测不等于再次执行整文件完整性校验。
- 2026-09-10：旧 Qt 6.11.2 链路中，销毁旧 `QAudioBufferOutput` 可能清掉播放器的新输出连接，导致后续歌曲无声。曾按“先断开、同步销毁旧对象、再连接新对象”修正；最终实际播放改用自有解码器直接交付 PCM。
- 2026-09-10：《翩翩.flac》在约 223190 ms 报错后仍继续播放，但旧恢复流程记住首次报错位置，尾部又因采样数不符否决完成，造成后段重复及最终停止。当前由解码器内部容错，保留后续有效数据；只有真实 EOF 和实际输出排空才结束，致命解码失败不再触发同曲重载。
- 2026-09-10：对《翩翩.flac》的只读检查发现至少一处 FLAC 帧 CRC 校验异常；用同一 FFmpeg 7.1.5 DLL 单独解码时记录到两次解码错误，同时取得四帧缺少时间戳但可解码的音频，共 18432 个采样帧。说明文件局部异常和播放链路对时间戳的处理需分别考虑；不能把 Qt 少输出的所有采样都认定为不可解码，也不能据此判断整个音乐库损坏或确定损坏发生在下载阶段。
- 用户提到 QQ 音乐或原声播放更顺畅；未比较 QQ 音乐的内部实现或实际输出，不将“它可以连续播放”当作文件无损的证明。实时容错可以保留有效声音、跳过损坏及短暂淡入，不能保证恢复已丢失的原始波形。本轮没有修复或替换任何音乐文件。
